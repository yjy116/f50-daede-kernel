# 后续维护必须保留的配置

用户要求保留当前可用配置；新的明确修改要求优先。每次升级使用当时设备的最新
设置，不得用 2026-10-11 的基线覆盖之后修改的密码、订阅或网络参数。

1. 检查运行版本、服务状态及未提交 UCI 修改；在设备运行已安装的
   `/etc/mu300/f50-profile/capture.sh` 创建唯一目录的新快照。Honk 将短暂停止并恢复。
2. 下载到私有目录。临时维护公钥不得留在长期备份：只删除本次公钥的精确匹配行，
   保留其他授权。生成与 `tools/verify_snapshot.py` schema 一致的清单，核验双端
   SHA、必需路径、SQLite 和隔离恢复。保留上一次验证成功的快照。
3. 核查候选镜像和实际系统差异。原生 `mu300-update apply` 不读取
   `sysupgrade.conf`/`keep.d`，会执行 boot_update；备份集成不等于升级保留。
4. 优先采用经过差异核查的用户空间迁移；整包 rootfs 更换需先合并当前用户设置、
   定制文件与兼容插件依赖，再切换。不要整体覆盖 `/etc` 或跨版本恢复旧 APK 数据库。
   新版 `image-version`/`packages.txt` 应保持新版本。
5. 保留 Honk 的 SIPA 修复、Doona 数据库、认证/订阅/路由/DNS、热点/蜂窝、设备身份、
   LuCI 温度 ACL/脚本、Doona 入口、mu300-hw 定制及服务启停状态。daede 已卸载，
   OpenClash 停用，不能在迁移中重新启用。电脑继续优先通过 WLAN 上网。
6. 单独保留 BPF JIT/BTF 内核和配套模块、BTF、设备 boot 材料。
   `MU300_KERNEL_BUNDLE` 不是无条件跳过 boot 刷写，需核对候选源码和 installed.id
   条件。换内核时重新验证 JIT/BTF、模块及 SIPA 数据通路，保留回退材料。
7. 切换前核验设置、认证数据库、定制文件和依赖；启动后检查 Honk/Doona、温度、
   菜单、热点、订阅、节点真实 HTTP/UDP DNS 及手机代理访问。进程存活或 API
   operation succeeded 不等于代理正常。
8. 保存验证证据。撤销本次临时 SSH 授权，确认新连接认证被拒绝，再删除本机临时密钥。
   若同步 GitHub，源码和摘要可公开；包含秘密的材料必须加密后作为 Release 附件，
   解密密钥仅由持有人私下保管。普通 `.gitignore` 不能替代逐文件发布检查。

保留已知缺陷：重启后偶发节点回程丢包仍待定位，不通过自动重拨隐藏故障。
历史 v17→v18 脚本是特定前提下的迁移记录，不应直接用于下一版本。
