# F50 官方完整升级记录：2026-10-31

设备已从定制内核基线切换并启动到官方 mu300-linux `v2026.10.30.1`、OpenWrt `25.12.6`
和 Linux `7.2.13`。新系统保留现有 SIPA 适配 Honk、Doona、插件和用户设置；当前完成
启动、插卡及随后带 SIM 重启的实网检查。两轮三个节点 HTTP/UDP DNS 和真实代理访问均通过，
用户关闭手机移动数据后也确认热点访问及界面正常。官方内核仍有进程识别能力限制，
不能宣称全部 Honk 功能兼容。订阅刷新后的节点与代理复测已通过，最终快照已捕获，
备份下载校验、加密与发布尚在完成中；本次成功
不等于历史偶发的重启回程丢包已永久修复。

## 配置和插件保留

使用设备本次设置构建隔离候选 rootfs，保留认证数据库、订阅、路由/DNS、热点/蜂窝、
设备身份、LuCI 温度和 Doona 入口及服务启停状态。`mu300-hw` 使用新版官方原文，
旧定制仅作为备份，不再运行。SQLite 在停止写入者
后校验，`integrity_check=ok`。公开报告不包含数据库、配置值、密码、订阅或设备私钥。

缺少的 83 个用户态插件/依赖按以下方式补齐，候选系统安装后共 321 包：

- 59 个来自 OpenWrt 25.12.6 官方 feed，精确下载共 9,878,627 字节。
- 22 个保留已验证的社区兼容包。部分官方同名包要求新 rootfs APK 数据库未提供的
  kmod，或与现有 LuCI 插件的精确版本依赖冲突；未通过安装其他内核模块解决。
- 2 个旧官方配套包：`iperf3/libiperf3 3.20-r1`，满足现有 LuCI iperf3 的精确依赖。
  仅通过 `legacy-iperf` 标签请求这两个包，不将旧 feed 作为普通升级仓库。

全部选定 APK 经独立签名或官方签名索引绑定、元数据和逐文件 payload 校验。
没有恢复旧 world 或旧 APK 数据库，没有用旧包回退新官方基础系统。
原 `dnsmasq` 换为插件所需 `dnsmasq-full`，所以包数为 `239 - 1 + 83 = 321`。

候选阶段逐项审查重新出现的首启初始化：跳过 10 项已完成的旧初始化，保留 31 项脚本，
避免 EasyTier 自动启用、HomeProxy/OpenClash 重写配置、Aurora 重置等再次覆盖用户设置。
首启后这 31 项均已执行，`/etc/uci-defaults` 为空，UCI 没有待提交修改。观察到的新配置差异
限于官方 Docker 配置、WAN zone 的设备项、日志大小和 AP U-APSD；设备身份、SSH 主机密钥
与 TLS 材料保持一致。
这一结果是本次具体脚本集合的审查记录，不能直接用于跳过下一版本的新迁移。

当前继续使用 `Honk debug.2026.10.9.native-api.2-f50-sipa1` 与 Doona `0.1.0-beta.19`。
daede 仍未安装，OpenClash 保留但停用。用户允许 Honk 不兼容时改用 daede，
但本次没有执行该替换，也没有以进程存活证明代理流量正常。

新官方 ADB 服务在缺少状态文件时默认允许 USB 上未认证的 root shell。本次明确设置
`/etc/mu300/adb=off`，维持原来的 NCM 网络和 ACM 串口管理，不新增该访问入口。
电脑继续以 WLAN 优先上网，USB 用于 F50 管理。

保留工具的 kernel bundle 路径已指向
`/mnt/mu300-disk/f50-official-20261031/mu300-kernel-7.2.tar.gz`，SHA 与上表一致。
旧 `7.2.9-f50-bpf1` 及更早构建只保留历史追溯，不作为后续部署或编译目标。

## 写入与实机启动证据

写入命令的原始执行记录为 `EXIT rc1`，该异常没有被改写成成功。随后独立读回核对
boot 正文、实际写入区、尾部及 installed.id 均通过，之后才以实机启动确认新内核生效。
此处不推定原非零退出的根因，也不把单一返回码作为分区内容的证明。

- boot 正文 SHA256：`53de3e50196ff83372c98faf9b90d7f1857d00388e8f071ec18dcdb84372dd31`。
- 实际写入区 SHA256：`c595e3806fb11bfdc60488816c67a34e50a3540f1b3ff1266e63c8d9e8de15b0`。
- boot 尾部 SHA256：`40108e70c2769ac93f059428d6c6b8b14b82235105feeb219530d3a0883b8688`。
- Android boot 分区读回未变化；misc 的试启动记录区 `[2048, 2080)` 读回符合预期，
  Linux 试启动次数为 5。旧状态已相同，因此 misc 整分区 SHA 未变；该范围是允许修改范围，
  不是本次实际发生变化的证明。
- 重启前核验记录覆盖 3,040 模块、94 官方程序和 99 配置项。

上述 API 的 5 项不是新增的 5 个远端节点，流量通过结论来自独立请求与回包证据，
不以 BPF 挂接或登录代替。首次组合 UDP DNS 探测确有异常：TUIC 请求超时，HY2 随后
耗尽共享 30 秒 deadline、尚未开始实际探测。该记录保留；后续按节点独立探测的 UDP DNS
全部通过，带 SIM 重启后六项检查也全部通过。不能把第一次组合测试改写为成功，
也不能把未开始的 HY2 探测当作该节点已实际请求失败。

官方内核因稳定性取舍关闭 `CONFIG_PERF_EVENTS`、`CONFIG_KPROBES`、`CONFIG_FTRACE`，
没有启用 `CONFIG_BPF_EVENTS`。Honk 获取完整 `argv` 的路径不可用，改用 `comm`，
API 明确报告 `pname_routing_reduced`。已复核的 2 条进程名规则涉及 `NetworkManager`、
`systemd-resolved` 和 `zerotier-one`：前两者当前未运行，正在运行的 `zerotier-one` 名称
为 12 字符，真实读取的 `comm` 已确认与规则短名一致。这一名字证据不等于所有进程路由
行为已逐项测试；未来涉及长名称或依靠 `argv` 区分进程的规则须重新验证。规则原文保持不变，
没有新增路由兜底来掩盖降级。
本次不为此编译内核，也未直接替换为 daede；不能宣称全部 Honk 功能兼容或该限制无影响。

订阅在 WAN 尚未就绪时启动抓取，曾处于 `stale`。WAN 联网后主动 refresh 已成功：
目标 provider 为 `ok`、包含 3 个节点、`error=null`。刷新更新了运行时节点 ID，不能声称
ID 始终不变；本次已重新发现节点，按新 ID 完成三节点 HTTP/UDP DNS 六项检查，全部通过。
Google HTTP 204、ipify HTTP 200 的流记录也再次满足 `outbound=proxy`、`reply_received=true`，
测试设置随后复原，没有以刷新前结果代替新 ID 的验收。

用户随后报告 ZeroTier 在线但两个目标访问异常。初测其中一个目标 ping 为 3/3、HTTP 200，
另一个目标的下一跳邻居状态为 `ARP FAILED`。用户随后报告自行恢复；复测两个目标均为
ping 2/2、HTTP 200，原失败的下一跳变为 `REACHABLE`。期间未修改 ZeroTier、Honk 或防火墙，
最终捕获的配置也未因这次诊断改变。证据支持曾有暂时的下一跳未响应及随后恢复，
不能据此断定唯一根因或永久修复；公开报告不展开用户私有网段与路由配置。

本地证据包括 `boot-write-verification.json`、`candidate-validation.json`、
`pre-reboot-validation.log`、`first-boot-runtime.log`，并结合主流程的节点探测、proxy flow、
重启、订阅刷新和用户手机验收记录。
公开文档仅保存必要摘要，不发布这些私有目录内容。
